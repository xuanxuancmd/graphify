# reverse-engineering-ddd 帮助文档

## 全局产物

### context-map.md — 业务边界图

**意图**：记录系统有哪些独立业务域、它们之间的协作关系、以及团队共用的业务术语表。这是知识库的"业务版图"——增量开发时先看此文件定位改动属于哪个业务域，避免跨域耦合。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **限界上下文**（Bounded Context） | DDD 战略设计的核心概念——一个业务领域中模型和语言保持一致的边界。不同上下文中的同名概念可以含义不同（如 `Order` 在订单上下文指订单，在物流上下文指配送指令）。划分限界上下文就是划分业务边界 |
| **统一语言**（Ubiquitous Language） | 团队在某个上下文内共用的业务术语表，确保所有人对同一概念有相同理解。同一个词在不同上下文含义可能不同——代码里都叫 `Order`，歧义只有人知道 |
| **战略分类**（Strategic Classification） | 将限界上下文分为三类：核心域（差异化能力，项目最重要的业务价值）、支撑域（必要但非差异化）、通用域（可被现成方案替换） |
| **客户-供应商关系**（Customer-Supplier） | 两个上下文间的业务关系：一方（客户）依赖另一方（供应商）的业务承诺，供应商有义务维护承诺 |
| **防腐层**（Anti-Corruption Layer, ACL） | 隔离外部上下文的翻译层，防止外部系统的模型"污染"本上下文的领域模型。当本上下文需要依赖外部系统时，通过防腐层将外部概念翻译为本上下文的语言 |
| **发布语言**（Published Language） | 上下文间通过一套共用的通信语言（标准协议/schema，如行业标准 XML、HL7、ISO 8583）交互，常与 OHS 配套——它描述的是语言层面的共享，不是消息投递机制 |

**审阅关注点**：BC 划分是否符合你对业务的理解？关系类型是否准确？统一语言是否有遗漏或歧义？

### technical-constraints.md — 技术约束

**意图**：从架构、算法、设计模式、并发模型、安全模型等角度，总结项目中该技术的解决的问题与选型理由、次要内容还包括编码规范、合规约束（依赖/兼容性限制）。代码能看出"用了什么技术"，但看不出"为什么选这个""踩过什么坑"——此文件承载这些隐性知识。本文不体现显而易见的共识性技术。

**拆分位置**：全局适用约束写入 `docs/technical-constraints.md`（L0 会话级预加载）；仅某个 BC 特有的约束写入 `docs/features/<bc>/technical-constraints.md`（开发该 BC 时读）。判断标准：适用于所有 BC → 全局；仅适用某 BC → BC 级。跨 BC 通用的约束（如全局错误处理规范）归全局文件，不误拆到 BC 下。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **trade-off 优先级** | 当代码中出现有意的场景化差异时（如不同模块用不同方案），记录取舍优先级——什么场景优先什么 |

**审阅关注点**：选型理由是否来自实际经验（非臆造）？有无遗漏的关键技术约束？是否有显而易见的冗余描述应该删除？

## BC 级产物

> 以下文件按限界上下文（BC）组织，位于 `docs/features/<bc-name>/` 目录下。每个 BC 独立一套。

### index.md — BC 入口速查

**意图**：该 BC 的入口文件，提供业务概要、关键概念、工件摘要、跨 BC 关系、技术契约索引的速查表。开发某 BC 时必读此文件，快速定位需要深入哪个具体工件，避免全载浪费上下文。

---

### domain-model.md — 领域模型

**意图**：记录聚合根如何协作完成业务用例、聚合边界、状态机、行为归属识别。代码结构查询（graphify）能给出字段级 ER 图，但查不出"为什么这些聚合要协作""行为应该在哪个对象上"——此文件承载业务级的"聚合为什么这么设计"。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **聚合**（Aggregate） | 一组相关对象的集合，作为一个整体维护一致性。聚合之所以是一个聚合，正是因为内部有"必须永远为真"的不变式规则需要一起维护 |
| **聚合根**（Aggregate Root） | 聚合对外的唯一入口——外部只能通过聚合根访问聚合内部对象。判断依据：被其他模块引用作为"入口"、有多个实体/值对象归属于它、有独立的 Repository |
| **聚合协作视图** | 展示聚合如何协作完成业务用例，以及依赖的业务性质（如"Worker 分配 依赖 Task 处于 Schedulable 状态"）。不产出字段级 ER 图——字段关系由 graphify 提供 |
| **聚合边界** | 哪些对象属于同一聚合——通过"是否一起加载/校验/持久化"判断。跨聚合通过 ID 引用而非直接持有对象引用是有意的边界设计 |
| **领域服务 vs 应用服务** | 领域服务承载业务规则（如 `PricingService.calculate(order)`）；应用服务只编排流程不含业务规则（如 `OrderAppService.placeOrder()`）。贫血模型下需区分两者，将领域服务的行为归入此文件 |
| **状态机** | 有状态实体的业务状态与转换——状态转换的业务触发条件、守卫条件的业务含义、为什么某些转换不允许。代码显示 `status` 字段和 `match` 逻辑，但不显示业务触发条件 |

**审阅关注点**：聚合边界是否正确？行为归属（贫血/充血）判断是否准确？状态机转换是否完整？是否状态机等描述是多余可删除？

**可空条件**：无聚合概念的过程式代码不生成此文件，在 index.md 标注 N/A。

### domain-events.md — 业务事件

**意图**：记录业务状态变更事件及其触发场景、失败/补偿事件。帮助理解"业务上发生了什么状态转换"——区分业务事件和基础设施事件，避免将技术事件误认为业务事件。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **领域事件**（Domain Event） | 业务上有意义的事情发生了——业务状态的变更，不是技术事件（如审计日志、缓存失效、CDC）。用于解耦上下文间的协作：发布方不需要知道谁订阅，订阅方按需响应 |
| **业务事件 vs 基础设施事件** | 业务事件描述业务结果或状态变更（如 `OrderPlaced`、`PaymentFailed`）；基础设施事件描述技术机制（如 `DatabaseTransactionCommitted`、`CacheInvalidated`）。只有业务事件记入此文件，但最终归属需用户确认——有些看似技术的事件在特定业务下是业务事件 |

**审阅关注点**：事件是否都是业务事件（非技术事件）？触发场景是否准确？有无遗漏的关键事件？

**可空条件**：无业务事件时不生成此文件，在 index.md 标注 N/A。

---

### contracts.md — 业务契约

**意图**：记录每个接口的业务承诺（不只是技术 API 签名，而是业务上的约定）以及跨上下文通信的方向和协议。代码只显示接口签名，不显示"调用这个接口的业务前提是什么""失败后业务上留下什么状态"——此文件承载这些业务承诺。

**与 swagger/openapi 的关系**：swagger/openapi 是技术层契约（端点路径、参数 schema、状态码），承载不了业务语义。contracts.md 补 swagger 表达不了的前置条件、后置条件的业务语义、失败语义（业务后果，不是错误码）、幂等性的业务含义。纯 CRUD、参数校验即全部的接口，contracts.md 标 N/A。contracts.md 不复述 swagger 已有的技术内容（端点路径、参数列表、状态码）——只补业务语义。`context-map.md §2.1` 登记 swagger 文件位置作为技术索引，contracts.md 的"契约定位符"列指向 swagger 端点。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **契约**（Contract） | 限界上下文间协作的明确约定——业务承诺，不只是技术 API 文档 |
| **前置条件**（Precondition） | 调用前必须满足什么业务状态——不满足则调用无意义或非法 |
| **后置条件**（Postcondition） | 调用后承诺什么业务状态——调用成功后状态必然变为这个 |
| **失败语义** | 失败时业务上留下什么状态——不只是错误码，而是业务后果（如"支付失败后订单保留，等待重试"） |
| **幂等性**（Idempotency） | 重复调用业务上是否安全——同一个操作调用一次和调用多次，业务结果是否相同 |

**审阅关注点**：前置/后置条件是否准确？失败语义是否符合业务实际？幂等性要求是否正确？是否复述了 swagger 已有的技术内容（应删除）？

**可空条件**：无跨上下文调用时不生成此文件，在 index.md 标注 N/A。

### invariants.md — 业务不变式

**意图**：记录"违反即业务状态非法"的业务规则，可以认为是业务的基本规格。帮助判断"什么必须永远为真"——增量开发时避免引入违反不变式的修改。严格区分三类规则，避免把防御性编程或接口契约当成不变式。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **不变式**（Invariant） | 聚合根对所有调用者的状态承诺——无论被怎么操作，状态永远满足这些规则。违反不变式意味着业务状态非法（不是错误，是状态破坏） |
| **契约 vs 不变式的边界判定** | 契约回答"单次调用后承诺什么"（调用前→执行→调用后）→ contracts.md；不变式回答"无论怎么操作，什么永远成立"（恒久为真）→ invariants.md。判定问句：① "这个规则违反后，业务对象即使重试或补偿也无法回到合法状态吗？" → 是 → 不变式；② "这条规则是单次调用前后的承诺吗？" → 是 → 契约 |
| **业务不变式 vs 接口契约 vs 防御性编程** | 三类规则性质不同：业务不变式恒久为真（违反即状态非法）→ 记入此文件；接口契约 → 归 contracts.md；防御性编程校验参数合法性（如"name 非空"）→ 不记录 |
| **事务边界** | 不变式是事务边界的判定依据——聚合之所以是一个聚合，正是因为内部有这些"必须永远为真"的规则需要一起维护。同事务内的多个写操作是因为不变式需要原子性 |
| **跨聚合不变式** | 两个聚合间的约束——如何维持？最终一致还是强一致？业务后果是什么？ |
| **跨 BC 不变式** | 跨上下文的约束——由谁保证？业务后果是什么？ |

**无状态业务无不变式**：不变式是聚合根概念。如果一个 BC 没有聚合根/有状态实体（纯计算、ETL、无状态转换 API、纯路由），不生成 invariants.md，在 BC index.md 标注 N/A。

**审阅关注点**：每条不变式是否真的是"违反即状态非法"（而非防御性编程或接口契约）？业务理由是否准确？有无遗漏的核心不变式？BC 无聚合根时是否已标注 N/A？

**可空条件**：无聚合根/无状态实体、无真正业务不变式、或仅显而易见规格时不生成此文件，在 BC index.md 标注 N/A。

### business-flow.md — 业务流程

**意图**：记录端到端用例的时序编排（业务上从哪开始、经过哪些关键步骤、到哪结束）、每步的业务理由（WHY）、失败时的补偿策略和业务后果。代码只显示方法调用顺序，不显示"为什么这么走"和"失败后业务上怎么办"，过程中仅体现关键节点，避免陷入细节。 ——此文件是唯一承载失败/补偿业务语义的产物。

**专业名词**：

| 名词 | 含义 |
|------|------|
| **业务流程**（Business Flow） | 跨聚合、跨上下文的协作叙事——不是方法调用链，而是"业务上从哪开始、经过哪些步骤、到哪结束"。每步都有业务理由（WHY） |
| **入口点** | 每个用例从哪里开始——应用服务方法 / 命令处理器 / 跨 BC 入站端口 / 周期任务 / 外部触发端点。这是 AI 增量开发时定位"在哪里加分支"的锚点 |
| **时序编排** | 用例的步骤序列——跨 BC 叙事，仅记录核心角色协作 + 业务理由，不写方法级细节（方法级细节交 graphify） |
| **补偿**（Compensation） | 失败时的正向操作以抵消已发生的效果。补偿 ≠ 回滚——回滚是恢复原状态，补偿是做反向操作抵消（如已扣款则退款，已发货则召回） |
| **Saga 模式** | 失败/补偿矩阵借鉴的模式——每个失败点有对应的补偿动作，补偿是否恢复原状态需标注 |

**审阅关注点**：流程步骤是否完整？失败补偿策略是否符合业务实际？每步的业务理由是否准确？步骤是否包含太多无效细节应予以删除？

**可空条件**：无任何关键业务用例（无跨 BC 协作、无失败补偿、无周期任务、无外部触发关键流程）时不生成此文件，在 index.md 标注 N/A。有关键业务流（含周期任务、外部触发）即使单 BC 内也必须生成。
