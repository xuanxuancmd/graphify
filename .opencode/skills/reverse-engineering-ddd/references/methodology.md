# 方法论参考

> 一次一问的共建方法论：模型探索漩涡 + 模糊性处理 + 临时文件与闭环删除。
> 首次遇到 STOP/ASSUME 决策时加载；Step 9 闭环前加载 §5-§6。

---

## §1 核心方法：模型探索漩涡

在澄清任何概念时（边界 / 统一语言 / 流程 / 不变式 / 约束），使用迭代循环：

1. **浮现**：从代码命名中提取候选概念（代码信号记录到 `draft/inferences-draft.md` 的信号区）
2. **探查**：带着代码信号问用户一个问题——"我读到 X，这是说……吗？"
3. **挑战**：找一个与提议含义矛盾的代码示例 → 请用户解决
4. **精炼**：根据用户回答更新理解
5. **验证**：找另一个代码示例确认精炼后的理解成立
6. **循环** 2-5 直到找不到矛盾 → 写入干净的产物

这通过强制在接受用户回答前寻找矛盾证据，防止肤浅的"是的，没错"确认。

### 代码信号的读取原则

- 读取的代码信号（目录、类型名、方法计数、命名模式）记录到 `draft/inferences-draft.md` 的信号区，可含 file:line
- 这些信号是**提问的依据**，在对话中展示给用户作为上下文
- 信号**不进入**产物文件
- 信号用于形成 `[INFERRED]` 候选语义（记录到 `draft/inferences-draft.md`），由用户确认后转为干净产物

### 提问素材的生成模式

对每类要提取的概念，遵循同一模式：

1. **扫描**：用 Glob/Read/graphify 读取代码信号
2. **形成候选**：从信号形成候选业务语义（`[INFERRED]`，记录到 `draft/inferences-draft.md`）
3. **找矛盾**：刻意找一个与候选语义矛盾的代码示例
4. **生成问题**：基于候选 + 矛盾，生成**一个**清晰的问题
5. **记录问题**：写入 `draft/questions-log.md`
6. **等回答**：一次一问，得到回答后再进入下一个

## §2 提问规则与格式

### 提问规则

- **一次只问一个问题。** 相关问题排成队列，问完一个、得到回答、达成一致后再问下一个。
- **先展示代码信号 → 再提问**（不要开放式提问）。代码信号展示在对话中，**不写入产物**。
- **给选项而非填空**，但允许用户给出第三种答案。
- **最大化代码提取以最小化用户负担** — 能从代码读出来的不问（调用关系、依赖、结构）。只问代码无法揭示的：业务意图、设计理由、bug 还是特性、业务规则、约束由来。
- **追求思想一致，不是 yes/no。** 如果用户只是说"对"，追问一个边界情况验证理解是否真的到位。
- **术语歧义/陌生必问，禁止瞎猜或忽略。** 遇到以下两种情况必须 STOP 提问，不得编造含义、也不得因"认识"而跳过：
  - **陌生私有术语**：代码中出现 AI 无法理解的业务专有名词、缩写或领域黑话。禁止臆造含义。当代码信号不足以形成任何候选语义时，直接询问"术语 X 在当前业务中具体指什么"。
  - **通用词歧义**：术语本身常见但过于宽泛（如"插件""事件""任务"），仅凭通用知识无法对应到当前服务的具体语义。必须带代码信号问"这里的 X 在当前业务上下文中具体指什么"。

  两种情况均按 STOP 处理——术语语义错误会级联到边界、流程、契约、不变式等上游工件，返工半径为 HIGH。

### 提问格式

```
我想理解 {概念}：

代码里我看到：{简述代码信号——这是临时展示，不进产物}
我的理解是：{用业务语言复述你的理解}

问题：{一个具体问题，附 A/B 选项}
如果错了的影响：{简述返工范围}
```

> 代码信号的展示是**对话内**的，用于让用户知道你读了什么、为什么这么问。它**不进入**任何产物文件。

## §3 模糊性处理：STOP vs ASSUME

### 核心判断标准：返工半径

不是"我有多大信心"，而是"如果错了，要扔掉多少工作"。

### Tier 1：STOP — 一次一问，立即确认

**判断标准：** 如果这个假设错了，跨多个步骤或 phase 的工作必须重做。

**STOP 触发条件：**
- 业务边界不匹配任何可识别的布局
- 一个概念可能属于两个不同 BC → 归属错误会级联
- 业务规则或事件的存在性存疑
- 上下文间通信应该同步还是异步不清
- 核心聚合边界不清
- 业务不变式解释模糊
- 任何"我用代码结构推业务语义"的推断——必须问用户
- 任何错误答案会使上游工件失效的模糊性

**行为：** 立即停下。提**一个**清晰的问题。不继续直到回答。记录到 `draft/questions-log.md`。

**一次一问规则：**
- 一次只问**一个** STOP 级问题
- 相关问题排成队列，问完一个、得到回答、达成一致后再问下一个
- 先展示代码信号 → 再提问（代码信号在对话内展示，不进产物）
- 给选项而非填空，但允许用户给出第三种答案

### Tier 2：ASSUME & RECORD

**判断标准：** 如果这个假设错了，只需改当前步骤或 phase 工件（返工半径 ≤ MEDIUM）。

**示例：** 命名选择、字段顺序、非关键实现细节、日志格式。

**行为：** 选最保守、最易改的选项。立即记录到 `draft/assumptions-draft.md`。继续。

**选择策略：** 拿不准时，选最易重命名或替换的选项。偏好通用名而非特定名。偏好简单结构而非复杂结构。

**[ASSUMPTION] 标记格式（在 `draft/assumptions-draft.md`）：**
```
[ASSUMPTION: {模糊点描述}]
├─ 选择: {选定的选项}
├─ 备选: {被拒绝的选项及原因}
└─ 变更成本: LOW（重命名/重格式） | MEDIUM（重构当前 phase 工件）
```

> 变更成本 HIGH 永远不出现在这里。HIGH 成本是 STOP 触发条件。

### 何时提问 vs 何时假设

| 等级 | 标准 | 行为 |
|:---|:---|:---|
| **STOP** | 错了 → 跨步骤/跨 phase 返工 | 立即问用户；一次一问；不继续 |
| **ASSUME & RECORD** | 错了 → 只修复当前工件 | 选最保守选项，记录到 draft，继续 |

> 真正不确定是 STOP 还是 ASSUME 时，按返工半径测试。错了是否迫使重新提取事件、重画边界、重新设计契约？是=STOP。否=ASSUME。倾向 STOP。

## §4 临时文件 vs 产物：清晰边界

### 临时文件（`docs/draft/`）—— 中间态，闭环即删

| 文件 | 内容 | 可含 |
|---|---|---|
| `inferences-draft.md` | 代码信号（目录、类型、方法计数、命名模式、扫描摘要）+ `[INFERRED]` 推断（从信号推出的候选业务语义） | file:line、模块路径、类型名、`[INFERRED]` 标记、置信度 |
| `assumptions-draft.md` | `[ASSUMPTION]` 假设：用户未明确但保守采用的决策 | `[ASSUMPTION]` 标记、变更成本 |
| `questions-log.md` | 已问问题与用户回答摘要 | 完整对话上下文 |

**临时文件的作用：**
- 承载所有中间态，让产物保持干净
- 支撑对话（代码信号在对话中展示，源头是 inferences-draft）
- 支撑会话恢复（questions-log 记录进度）
- 闭环后删除，产物成为唯一权威

### 产物文件 —— 干净态，长期保留

产物文件（`context-map.md`、`technical-constraints.md`、`features/**/*.md`）**禁止出现**：

- `file:line` 代码定位
- 代码段粘贴、方法签名参数列表、字段列表
- `[INFERRED]`、`[OBSERVED]`、`[ASSUMPTION]` 等中间态标记
- "待实现"、"后续补充"、"待确认"等占位描述
- 置信度标记（已确认即无不确定，未确认不进产物）
- **填写指引 blockquote**（如"代码结构由 graphify 提供，不在此处复述"、判定规则表、列含义说明）——模板即产物结构，填写方法在 references 参考文档中，不随模板复制到产物
- **自检章节**（如"待澄清项"）——过程跟踪在 `draft/` 临时文件中
- **导航元信息**（如"返回 [SKILL.md]"、"L1 始终加载"）——产物独立存在，不需导航回 skill
- **状态跟踪字段**（如"状态: 已确认"）——已确认是默认态，无需标注；UNKNOWN 直接写在理由字段中

**允许引用的代码锚点**：包名/模块路径、类名/类型名、trait/接口名、关键 public 方法名、REST 端点路径、表名、配置文件路径——这些命名是业务概念的承载者，便于后续 AI 从产物跳转到代码。

#### 代码锚点引用决策树

对任何一个代码命名，按以下顺序判断是否应作为锚点引用到 DDD 产物：

1. **它是业务概念的承载者吗？**（如类型名承载业务概念名、事件名承载业务事件）
   → 是 → 引用（进 `domain-model.md` / `domain-events.md`）
2. **它是外部入口的标识吗？**（如 REST 端点路径、trait 名、事件 topic）
   → 是 → 引用（进 `contracts.md` / `context-map.md` OHS 实现列）
3. **它是业务规则的定位点吗？**（如守卫方法名、领域服务方法名）
   → 是 → 引用（进 `invariants.md` 校验位置 / `domain-model.md` 领域服务）
4. **它是业务流程的编排点吗？**（如应用服务方法名、命令处理器类名）
   → 是 → 引用（进 `business-flow.md` 代码锚点列）
5. **它是技术约束的配置锚点吗？**（如构建配置、CI 配置文件路径）
   → 是 → 引用（进 `technical-constraints.md` 配置锚点字段）
6. **以上都不是** → 不引用，归 graphify / 读源文件（如字段列表、方法签名参数、函数体、FK 关系、列类型）

**核心准则**：引用的是"命名"（业务概念的承载者、入口标识、规则定位点），不是"结构"（字段、参数、代码体）。命名是 AI 从产物跳转到代码的索引；结构是 graphify 的职责。

**产物文件只含：** 经用户确认的知识——业务边界、统一语言定义、业务流程叙事、业务不变式、契约承诺、业务事件、聚合协作、技术约束，以及上述代码锚点引用。

#### 表格标签体系

BC 级产物的表格标签遵循**三标签一组原则**：每张表要么三个标签全有，要么三个标签全无。不允许只打部分标签。

| 标签 | 含义 | 列内容 | 列名要求 |
|---|---|---|---|
| `<anchor:ddd>` | DDD 业务概念标识 | 唯一键，**业务术语**（非代码类名、非 ID），支持语义检索。**特例**：当代码类名本身就是业务术语时（如领域事件名采用 DDD 标准命名约定 `ConnectorStarted`，或 Kafka 生态中 `Worker`/`Connector`/`Task` 等类名即通用术语），可使用类名。判断标准：该名称在项目领域中有明确的业务含义，而非纯实现描述（如 `InternalSinkRecord` 是实现描述，非术语） | **列名必须精确**——列名前的汉字会作为图谱类别关键词提取，禁止过于通用（如"从""入口点""事件名"等），需带足够限定词（如"用例入口""跨BC契约""领域事件"等） |
| `<anchor:code>` | 代码锚点 | **仅支持三类格式**（大小写敏感）：`类名`（如 `WorkerConnector`）、`类名.函数名`（如 `Worker.start_connector`）、`HTTP方法:/路径`（如 `POST:/connectors`）。禁止文件路径、`文件#类名`、`模块路径#Trait`等其他格式 | — |
| `<anchor:desc>` | 业务语义描述 | 按产物类型指定的主 desc 字段——**该列内容将作为图谱入库的主描述字段**，须选择最能代表该实体业务语义的列 | — |

**白名单**（参与校验的产物）：`business-flow.md` / `invariants.md` / `contracts.md` / `domain-events.md` / `domain-model.md`

**豁免**（不参与校验）：`context-map.md`（索引文档，无代码锚点）、`technical-constraints.md`（子节列表式）、`index.md`（索引文档）

**表级豁免**（白名单产物中不参与校验的表）：`domain-model.md` 中的**行为归属表**——该表是聚合根/实体的附属属性说明，非独立可检索实体，三个标签全部移除。

**各产物 `<anchor:ddd>` 列名与 desc 字段**：

| 产物 | 表 | `<anchor:ddd>` 列名 | `<anchor:desc>` 列 |
|---|---|---|---|
| business-flow.md | 入口点表 | 用例入口 | 业务触发 |
| business-flow.md | 时序编排表 | 业务动作 | 业务理由（WHY） |
| business-flow.md | 失败/补偿矩阵 | 失败点 | 业务理由 |
| invariants.md | 不变式目录 | 业务不变式 | 业务理由 |
| contracts.md | 跨BC契约表 | 跨BC契约 | 业务承诺 |
| domain-events.md | 业务事件表 | 领域事件 | 业务触发场景 |
| domain-model.md | 聚合根表 | 聚合根 | 业务职责（一句话） |
| domain-model.md | 领域实体表 | 领域实体 | 业务职责 |
| domain-model.md | 值对象表 | 值对象 | 业务含义 |
| domain-model.md | 聚合协作视图 | 聚合协作 | 业务性质 |
| domain-model.md | 状态机表 | 状态转换 | 守卫条件（业务含义） |
| domain-model.md | 领域服务表 | 领域服务 | 业务行为 |
| domain-model.md | 行为归属表 | （无标签） | （无标签） |

**锚点定位规则**：

- **flow 调用链**：入口点表代码锚点列记入口类.方法；时序编排表代码锚点列填该步入口方法（`类名.函数名`），若跨类调用链在"业务理由"中补充"调用链：A.method → B.method"
- **invariants 部分实现**：每条不变式必须定位到一个 enforce 函数（`类名.函数名`）。若由构造函数或类型系统保证，填 `类名`。无法定位时 STOP 向用户核实
- **events 发布点**：代码锚点填事件发布点所在函数（调用 publish/emit 的代码位置）
- **domain-model**：聚合根/领域实体/值对象/领域服务填 `类名`；聚合协作视图/状态机填 `类名.函数名`（发起协作/执行转换的方法）

### 何时写入产物

**只有用户确认后**才写入产物。流程：

1. 读码 → 代码信号写入 `draft/inferences-draft.md` 的信号区
2. 形成候选语义 → `[INFERRED]` 写入 `draft/inferences-draft.md`
3. 一次一问 → 用户回答写入 `draft/questions-log.md`
4. 达成共识 → **干净的结论**写入产物文件（无中间态标记、无代码段粘贴；允许引用代码锚点）
5. 对应的 `[INFERRED]` 在 `draft/inferences-draft.md` 标记为"已转为产物"

## §5 假设累积与评审门禁

### 假设累积机制

#### assumptions-draft.md

- **位置：** `docs/draft/assumptions-draft.md`
- **何时写入：** 每次做出 ASSUME & RECORD 决策时，立即将 `[ASSUMPTION]` 条目追加到此文件
- **格式：** 按 phase 分组
- **可见性：** 开发者可在工作流期间随时查看此文件

假设在 Step 2-8 期间静默累积。它们**不**在每个 step 单独呈现。Step 9 的假设评审门禁是统一呈现时刻。

### 假设评审门禁（Step 9）

此门禁在 Step 9（闭环）执行，是所有累积 ASSUME 决策呈现给人工审查的唯一时刻。

**流程：**

1. 将所有产物（已干净）和 `draft/assumptions-draft.md` 呈现给开发者
2. 开发者审查每个 `[ASSUMPTION]` 条目：✅ 保持 | ✏️ 改为：[替代方案]
3. 对任何修改的条目：执行返工影响检查。如果变更影响上游产物，回滚到该 phase 并重新执行
4. 所有条目确认后：将确认结果反映到产物（如有变更）

**如果任何检查失败 → STOP。在假设评审门禁完成前不要结束。**

## §6 闭环删除协议

> SKILL.md 的 Step 9 引用本节。

当 Step 9 假设评审门禁通过后，执行闭环删除：

### 删除前检查

1. **假设已评审**：`draft/assumptions-draft.md` 中所有条目状态为 ✅ 保持 或 ✏️ 已改
2. **推断已落定**：`draft/inferences-draft.md` 中所有 `[INFERRED]` 标记为"已转为产物"或"已否决"
3. **产物已干净**：所有产物文件通过全局产物干净度检查（无 file:line、无中间态标记、无代码段粘贴）
4. **AGENTS.md 已更新**：知识库指引段落已追加到项目根目录的 AGENTS.md（含 context-map/technical-constraints 作用与 BC 定位方法）

### 删除操作

删除整个 `docs/draft/` 目录。

### 删除后

- 产物文件成为唯一权威
- 后续 AI 加载知识库时只读产物
- 代码细节查询交给 graphify 或 Glob+Read+Grep

## §7 持久化防御与自检

### 自检协议

**在所有 step 的 phase 门禁处强制执行。**

每个 step 完成、进入下一步前，必须执行此验证序列：

1. **产物干净**：该 step 的产物文件不含 file:line、代码段粘贴、`[INFERRED]`/`[OBSERVED]`/`[ASSUMPTION]` 标记、填写指引 blockquote、自检章节、导航元信息、状态跟踪字段。允许引用包名、类名、方法名、接口名、端点路径、表名、配置文件路径作为代码锚点。UNKNOWN 直接写在理由字段中。显而易见的规格不记录。
2. **临时留痕**：代码信号 + 推断在 `draft/inferences-draft.md`，假设在 `draft/assumptions-draft.md`，提问在 `draft/questions-log.md`
3. **一次一问**：本轮对话每次只问了一个问题（查 `draft/questions-log.md`）
4. **无虚泛内容**：无"待实现"/"后续补充"/"丰富的行为"等虚泛描述
5. **表格优先**：简单业务表格足矣，仅复杂场景展开详情子节；文档体量与业务复杂度匹配

**任何检查失败 → STOP。修正。不进入下一步。**

### 持久化原则

- 每个 step 的产物确认后，立即将**干净版本**写入磁盘
- 不要在会话结束时才统一写——上下文重置会丢失所有未写入的工作
- 持久化的产物是权威的——会话恢复时读取它们确定进度，不重新扫描已完成步骤
- 临时文件也要即时写入——它们承载会话恢复所需的对话进度

## §8 反自我合理化

这些是 Agent 用来绕过此协议的真实借口。每一个都是错的。

| 借口 | 现实 |
|:-------|:--------|
| "产物里标个 file:line 方便反查" | file:line 是中间态证据，属 draft/。但产物应引用包名/类名/方法名/端点路径等代码锚点——这是命名引用，不是代码结构复述，便于后续 AI 定位代码 |
| "我把 `[INFERRED]` 留在产物里方便看置信度" | 产物是已确认态。未确认的不该进产物；已确认的不需要标记。中间态属于 `draft/` |
| "一次性呈现所有 BC 映射让用户确认更高效" | 一次一问才能达成思想一致。批量确认导致肤浅的"都对" |
| "这个模糊性很小，不用记录" | 每个未记录的假设都是不可见的技术债。开发者无法审查从未写下的东西 |
| "STOP 打断流程，我先做完再问" | STOP 级假设错误时的返工成本远超暂停提问的成本 |
| "我到最后再记录假设" | "到最后"永远不会来。上下文重置丢失所有未写入的假设。每次 ASSUME 决策时立即记录到 `draft/` |
| "方法数 8 个 → 核心域，不用问用户" | 从 WHAT 推 WHY 必然出错。核心/支撑/通用是业务判断，问用户 |
| "字段级 ER 图有助于理解数据模型" | 字段关系 graphify 一查就有。本 skill 产聚合协作视图——业务级"为什么连" |
| "HIGH 置信度不需要问用户" | HIGH 是强代码信号，不是业务确认。业务语义需人确认 |
| "决策理由我猜一个合理的" | 决策理由代码里不存在。臆造即伪造。问用户，不知道就标 UNKNOWN |
| "代码结构能推出业务流程" | 代码显示方法调用顺序，不显示业务叙事和"为什么这么走"。流程需共建 |
| "我对所有东西都 STOP 以保安全" | 过度 STOP 也是错的。对 ASSUME 级别的项阻塞造成不必要的摩擦。应用返工半径测试 |
| "这个是边界情况——我不确定是 STOP 还是 ASSUME" | 按返工半径测试。错了是否迫使重新提取事件、重画边界、重新设计契约？是=STOP。否=ASSUME。真正不确定时，倾向 STOP |
| "临时文件最后再删也行，留着方便追溯" | 闭环不删则产物与临时态混杂，后续 AI 无法区分已确认与未确认。闭环即删是硬门禁 |
| "这个词很常见我认识，不用问" | 通用词（插件/事件/任务/连接器）在不同业务上下文含义不同。"认识"≠"理解当前语义"。必须带代码信号问用户 |
| "这个陌生术语我猜个合理含义" | 私有术语的含义代码里不存在。臆造即伪造。无法形成候选时直接问，不编造 |
| "`<anchor:ddd>` 列填代码类名就行" | `<anchor:ddd>` 是 DDD 业务概念标识，须填**业务术语**，不是代码类名。代码类名归 `<anchor:code>` 列。两列填一样的内容就失去了分离的意义。**特例**：当代码类名本身就是业务术语时（如领域事件名 `ConnectorStarted`，或 Kafka 生态中 `Worker`/`Connector` 等类名即通用术语），可使用类名。判断标准：该名称在项目领域中有明确的业务含义，而非纯实现描述（如 `InternalSinkRecord` 是实现描述，非术语） |
| "代码锚点填文件路径或 `文件#类名` 更精确" | 代码锚点**仅支持三类格式**：`类名` / `类名.函数名` / `HTTP方法:/路径`。文件路径、`文件#类名`、`模块路径#Trait` 等格式一律禁止——文件路径信息归 graphify |
