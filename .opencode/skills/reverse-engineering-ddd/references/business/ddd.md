# 业务约束提取参考（DDD）

> 从代码读取信号、生成提问素材、共建业务约束的详细方法指导。按需加载对应章节。
> Step 2-7 的详细实现步骤与模式识别合并于此。

---

## §1 方法论：读码是为了问对问题

### 核心转变

本 skill **不从代码推断业务结论**。代码读取的唯一目的是**生成好的提问素材**：

- 代码告诉你 WHAT（有什么类型、什么方法、什么调用）和 HOW（如何实现）
- 代码**不告诉你** WHY（为什么这么设计）、SO-THAT（为了达成什么业务目的）、RULES（什么必须永远为真）
- 只有用户能回答 WHY/SO-THAT/RULES

因此，读码的产出是**问题清单**（代码信号 + 推断记录到 `draft/inferences-draft.md`），不是结论。

### 重建顺序

1. **业务边界**先 — 确定有哪些限界上下文，才知道去哪里找其他东西
2. **业务流程**次 — 端到端用例叙事揭示 BC 间如何协作
3. **契约**第三 — 业务承诺与通信方向
4. **事件**第四 — 业务状态转换
5. **聚合协作**第五 — 业务级聚合如何协作完成流程
6. **不变式**第六 — 流程和模型中浮现的"必须永远为真"

## §2 代码信号读取与提问素材生成

### 代码信号的读取原则

- 读取的代码信号（目录、类型名、方法计数、命名模式）记录到 `draft/inferences-draft.md` 的信号区，可含 file:line
- 这些信号是**提问的依据**，在对话中展示给用户作为上下文
- 信号（file:line、扫描摘要）**不进入**产物文件
- 信号用于形成 `[INFERRED]` 候选语义（记录到 `draft/inferences-draft.md`），由用户确认后转为干净产物

### 提问素材的生成模式

对每类要提取的概念，遵循同一模式：

1. **扫描**：用 Glob/Read/graphify 读取代码信号
2. **形成候选**：从信号形成候选业务语义（`[INFERRED]`，记录到 `draft/inferences-draft.md`）
3. **找矛盾**：刻意找一个与候选语义矛盾的代码示例
4. **生成问题**：基于候选 + 矛盾，生成**一个**清晰的问题
5. **记录问题**：写入 `draft/questions-log.md`
6. **等回答**：一次一问，得到回答后再进入下一个

## §3 模式识别：限界上下文（Step 2）

### 目录结构信号

| 代码信号 | 提问方向 | 问题示例 |
|:-------|:------|:------|
| `internal/{name}/domain/` + `internal/{name}/adapter/` | 六边形架构，`{name}` 是否是独立 BC？ | "我看到 `X` 有独立的 domain 和 adapter，它是一个独立的业务能力域吗？" |
| `src/{name}/` 含独立 entity/service/repository | 分层架构，`{name}` 是业务边界还是技术分层？ | "`X` 是按业务概念组织的，还是只是技术层？" |
| `pkg/{name}/` / `services/{name}/` / `modules/{name}/` | 可能是 BC 或部署单元/技术模块 | "`X` 是一个可独立演进的业务域，还是共享工具/部署单元？" |
| `controllers/` + `models/` + `services/` | MVC，无领域边界 | "项目似乎按技术层而非业务域组织。业务上你如何划分能力边界？" |

> 代码信号是**候选**，不是确认的 BC。命名"明显"也要问——`services/order/` 可能是订单 BC，也可能只是无领域边界的 CRUD 模块。

### 战略分类 — 必须问用户

**不从方法数推断核心/支撑/通用。** 代码信号只用于生成问题：

| 代码信号 | 提问方向 |
|:-------|:------|
| 高行为密度（聚合上 5+ 方法）、复杂不变式、领域特定错误、大量测试 | "这块代码投入很大，它是你最核心的差异化能力吗？" |
| 中等方法数、简单校验、服务于其他模块 | "这块似乎是为其他能力服务的，它是支撑性的吗？" |
| 薄封装、标准 CRUD、可被库替换 | "这块是否可以用现成库替代？还是含有定制逻辑？" |

### 关系类型 — 问业务性质

代码 import 方向揭示**技术**依赖，但**业务**关系性质需问用户：

| 代码信号 | 提问方向 |
|:---------|:------|
| A 导入 B 的 port 接口 | "A 调用 B 是客户-供应商关系（A 依赖 B 的承诺）吗？" |
| 跨聚合类型在共享包 | "这些共享类型是 Shared Kernel（共同维护）吗？谁主导？" |
| `adapter/acl/` 或 `adapter/translator/` | "这里有防腐层，是为了隔离哪个外部上下文？" |
| B 订阅 A 的事件 | "A 和 B 是发布订阅关系吗？业务上谁触发谁？" |

### 统一语言 — 从命名提取候选术语

从以下代码元素提取**候选**术语（确认后才是统一语言）：
- 类型名、方法名、枚举值、常量名、包/模块名

**关键提问**：跨 BC 歧义——同一个词在不同上下文中含义可能不同。代码无法揭示这种歧义，必须问。

> 例：`Order` 在订单上下文指订单，在物流上下文指配送指令。代码里都叫 `Order`，歧义只有人知道。

### Step 2 实现指导：共建业务边界图

对每个识别的候选 BC，通过一系列**一次一问**的对话澄清：

1. **BC 边界**：这个目录聚簇涵盖哪些业务概念？
2. **战略分类**：这是核心域、支撑域还是通用域？（问用户，不从方法数推断）
3. **关系**：BC 间是什么业务关系？（客户-供应商、ACL、发布订阅等——问业务性质，不是 import 方向）
4. **统一语言**：关键业务术语的定义与跨 BC 歧义

每个推断记录到 `draft/inferences-draft.md`，每个问题记录到 `draft/questions-log.md`。**用户确认后**，将干净的结论（无中间态标记、无代码段粘贴）写入 `context-map.md`。允许引用包名/类名/方法名等代码锚点。

**补充：对外契约文件清单（context-map.md §2.1）**

确定 BC 边界后，**必须**扫描每个 BC 对外暴露的技术契约文件（openapi/swagger、proto、graphql schema、asyncapi yaml、trait 定义等），登记到 `context-map.md` §2.1 表中。这是 Step 4（契约）正向索引的基础，也是 AI 增量开发时从 swagger 反查 BC 的入口。

**产出**：`docs/context-map.md` — 模板 [templates/business/context-map.md](../../templates/business/context-map.md)

## §4 模式识别：业务流程（Step 3）

### 从代码读取流程信号

| 代码信号 | 提问方向 |
|:---------|:------|
| 应用服务/命令处理器的方法序列 | "这个方法调用了 A→B→C，这是完整的业务流程吗？还是有前置/后置步骤代码外？" |
| 跨 BC 的调用链 | "这个跨上下文调用是流程的哪一步？业务上为什么需要这一步？" |
| 异步消息发布/订阅 | "这个异步通信对应业务流程的哪个断点？为什么在这里异步？" |
| 状态字段转换 | "状态从 A 到 B 的转换，业务上是由什么触发的？" |

### 流程叙事的共建

代码只显示方法调用顺序，**不显示**：
- 流程的业务起止点（从哪开始、到哪结束才算"完成"）
- 业务参与者（谁触发、谁受益）
- 跨 BC 步骤的业务必要性（为什么这一步要交给那个 BC）
- 失败/补偿路径的业务语义（不是错误码，是业务后果）

这些都需要一次一问地与用户共建。

### 提问示例

> 我想理解订单履约流程。
>
> 代码里我看到：`placeOrder` → `reserveInventory` → `processPayment` → `shipOrder`。
> 我的理解是：这是从下单到发货的完整流程。
>
> 问题：如果 `processPayment` 失败，业务上应该回滚库存预留，还是保留预留等待重试？（A: 回滚 / B: 保留重试 / C: 其他）

### Step 3 实现指导：共建关键业务用例

> **business-flow.md 的承载边界**：只承载关键业务用例时序编排 + 失败/补偿矩阵 + 每步业务理由（WHY）。**概念映射**：时序编排→DDD Application Service（应用服务编排用例）；跨 BC 协作→DDD Domain Event（领域事件驱动跨 BC 通信）；失败/补偿→Saga 模式（非 DDD，源自 Garcia-Molina & Salem 1987）。User Story/单场景业务说明归 .feature 的 Description 字段（见 harness-karate-design 文档），聚合静态结构归 domain-model.md，单接口承诺归 contracts.md。

对每个核心 BC，通过一次一问澄清**关键业务用例**，按以下结构共建：

1. **用例识别**：这个 BC 支撑哪些业务用例？（每个用例独立成节，分配用例 ID `UC-{BC编号}-{序号}`）。**必须覆盖**：跨 BC 流程、失败补偿场景、周期任务、外部触发的关键流程——即使单 BC 内的周期任务（如订单超时关闭、库存对账、结算跑批），只要是关键业务流，必须录入 business-flow.md。心跳检测、指标上报等基础设施定时任务不算。
2. **入口点**：每个用例从哪里开始？（应用服务方法 / 命令处理器 / 跨 BC 入站端口 / 周期任务 / 外部触发端点）——入口锚点必填，这是 AI 增量时定位"在哪里加分支"的锚点
3. **时序编排**：每个用例的步骤序列是什么？（跨 BC 叙事，不是方法调用链；仅记录核心角色协作 + 业务理由 WHY，不写方法级锚点）
4. **失败/补偿矩阵**：每个失败点的业务后果 + 补偿动作 + 补偿是否恢复原状态 + 业务理由（借鉴 Saga 模式——补偿 ≠ 回滚）

**注意：**
> 避免时序图过于详细，细节模型应该询问graphify图谱组件，这里的时序图是梗概，仅包含关键流程节点，次要节点不包含。
> 关联契约/事件索引、可执行规格反向链接为可选项，复杂场景按需补充，简单流程不记录。

> 代码只能告诉你方法调用顺序，业务流程叙事需要人来确认"为什么这么走"。
> 失败/补偿的业务语义（不是错误码）是本产物的核心独占价值——其他产物无法承载。

**产出**：各 BC 的 `docs/features/<bc-name>/business-flow.md` — 模板 [templates/business/business-flow.md](../../templates/business/business-flow.md)

## §5 模式识别：契约（Step 4）

### 端口接口信号

| 代码信号 | 提问方向 |
|:---------|:------|
| `trait *Port` / `interface *Port` | "这个端口代表对外的什么业务承诺？" |
| `trait *Repository` | "这个仓库是上下文内持久化，还是跨上下文数据访问？" |
| `trait *Gateway` | "这个网关对接的外部系统，业务上扮演什么角色？" |
| 边界结构体（DTO） | "这个 DTO 的字段组合代表什么业务概念？" |

### 区分上下文内 vs 跨上下文 — 问用户

- 端口方法使用**自己 BC 词汇表**的类型 → 候选：上下文内端口
- 端口方法使用**另一 BC 词汇表**的类型 → 候选：跨上下文端口

但"词汇表归属"本身可能模糊，需问用户确认。

### 契约的业务语义 — 必须问

代码显示接口签名，**不显示**：
- 前置条件（调用前必须满足什么业务状态）
- 后置条件（调用后承诺什么业务状态）
- 失败语义（失败时业务上留下什么状态，不只是错误类型）
- 幂等性的业务含义（重复调用业务上是否安全）

这些需一次一问共建。

> **与 swagger/openapi 的关系**：swagger/openapi 是技术层契约（端点路径、参数 schema、状态码），承载不了业务语义。contracts.md 补 swagger 表达不了的前置/后置条件的业务语义、失败语义（业务后果，不是错误码）、幂等性的业务含义。纯 CRUD、参数校验即全部的接口，contracts.md 标 N/A。contracts.md **不复述** swagger 已有的技术内容（端点路径、参数列表、状态码）——只补业务语义。`context-map.md §2.1` 登记 swagger 文件位置作为技术索引，contracts.md 的"契约定位符"列指向 swagger 端点。

### Step 4 实现指导：共建业务契约

对每个 BC，通过一次一问澄清**业务承诺**：

1. 这个 BC 对其他 BC 做了哪些业务承诺？
2. 通信方向与同步/异步的业务含义？
3. 失败时的业务后果（不是错误码）？
4. 幂等性的业务语义？

代码中的端口接口是提问素材（记录到 `draft/inferences-draft.md` 的信号区），契约的业务语义需用户确认后写入产物。

### 技术契约关联（Step 4 子步骤）

业务契约建立后，**必须**将业务契约与技术契约文件关联：

1. **扫描技术契约文件**：在每个 BC 内查找 openapi/swagger yaml、proto 文件、graphql schema、asyncapi yaml、trait 定义等
2. **登记到 `context-map.md` 的 §2.1 对外契约文件清单**：每个 BC 暴露的契约文件位置
3. **在 `contracts.md` 跨 BC 契约表中填写协议 + 契约定位符 + operationId**：
   - 协议类型：openapi / grpc / graphql / asyncapi / trait / interface / event / cron / 其他
   - 定位符格式：`{file}#{anchor}` 或 `{module}#{TraitName}.{method}`
4. **在 BC `index.md` 技术契约索引节建立 operation → 业务契约反向映射**（推荐项非强制——契约文件不可编辑如自动生成时，仅靠 contracts.md 的正向索引即可）

**产出**：各 BC 的 `docs/features/<bc-name>/contracts.md` — 模板 [templates/business/contracts.md](../../templates/business/contracts.md)

## §6 模式识别：业务事件（Step 5）

### 事件类型信号

| 代码信号 | 提问方向 |
|:---------|:------|
| 名为 `*Event`、`*Created`、`*Updated`、`*Cancelled`、`*Failed` 的类型 | "这是业务状态变更事件，还是技术事件（审计/CDC/指标）？" |
| 命令处理器（`Handle*`、`Create*`、`Process*`） | "这个命令的业务触发场景是什么？" |
| 事件发布调用 | "这个发布点对应业务流程的哪一步？" |
| 事件订阅注册 | "订阅方对这个事件做什么业务反应？" |

### 过滤基础设施事件 — 需用户确认

| 候选业务事件 ✅ | 候选基础设施事件（需确认过滤） |
|:-------|:------|
| `OrderPlaced` — 业务发生了 | `DatabaseTransactionCommitted` — 技术的 |
| `PaymentFailed` — 业务结果 | `CacheInvalidated` — 技术的 |

**规则**：如果事件名描述业务结果或状态变更 → 候选业务事件。如果描述技术机制 → 候选基础设施事件。**但最终归属需用户确认**——有些看似技术的事件在特定业务下是业务事件。

### 事件命名

产物中用过去时：`OrderPlaced`（不是 `PlaceOrder`）。

### Step 5 实现指导：共建业务事件

通过一次一问澄清**业务状态转换**：

1. 这个 BC 有哪些业务事件（业务状态变更，非技术事件）？
2. 每个事件的触发业务场景？
3. 失败/补偿事件？

> 基础设施事件（审计日志、CDC、指标）不是业务事件，过滤掉。

**产出**：各 BC 的 `docs/features/<bc-name>/domain-events.md` — 模板 [templates/business/domain-events.md](../../templates/business/domain-events.md)

## §7 模式识别：聚合协作（Step 6）

### 聚合根信号

| 代码信号 | 提问方向 |
|:-------|:------|
| 类型被其他模块引用作为"入口" | "这是这个上下文的核心入口概念吗？" |
| 类型有多个实体/值对象归属于它 | "这些附属概念是否应该在同一聚合内？" |
| 类型有独立的 Repository | "这个独立仓库是否意味着它是聚合根？" |

### 聚合协作视图 — 本 skill 的核心产出

**不产出字段级 ER 图。** 字段关系、外键、表结构由 graphify 提供。

本 skill 产出**聚合协作视图**：展示聚合如何**协作完成业务用例**，以及依赖的**业务性质**。

| 协作模式 | 提问方向 |
|:---------|:------|
| 聚合 A 在流程中调用聚合 B | "A 依赖 B 的什么业务能力？这个依赖的业务理由是什么？" |
| 聚合 A 引用聚合 B 的 ID | "A 只持有 B 的标识，业务上 A 和 B 是什么关系？" |
| 聚合 A 的状态依赖聚合 B 的状态 | "A 的状态转换需要 B 处于什么状态？这是业务规则吗？" |

### 聚合边界 — 通过聚合根表和协作视图隐式表达

聚合边界（哪些实体/值对象属于同一聚合）通过**聚合根表**的 ID 和**领域实体表/值对象表**的"归属聚合"列隐式表达，不再单独产出聚合边界表。跨聚合引用通过**聚合协作视图**表达。

> **移除原因**：原聚合边界表的信息与领域实体表（"归属聚合"列）、值对象表（"归属聚合"列）、聚合协作视图（跨聚合引用）冗余，且业务理由列容易过于通用（"是一个完整业务单元"），缺乏实际约束价值。

### 状态机 — 问业务触发

代码显示 `status` 字段和 `match status` 逻辑，**不显示**：
- 状态转换的业务触发条件
- 守卫条件的业务含义
- 为什么某些转换不允许

需一次一问共建。

### 行为归属识别（贫血/充血模型）

> **关键陷阱**：graphify 能查到实体/聚合根的类型和方法，但如果项目是**贫血模型**，实体的业务行为在外部 Domain Service 里，只读实体方法会**漏掉真实业务行为**。必须同时扫描外部 Service。

#### 识别模式

| 代码信号 | 模型类型 | 提问方向 |
|:---------|:------|:------|
| 实体/聚合根上有业务方法（`order.cancel()`、`task.assign(worker)`） | **充血模型** | "这些行为在实体上，是有意为之的领域模型设计吗？" |
| 实体只有 getter/setter，业务逻辑在 `*Service`/`*Manager`/`*Handler` 里 | **贫血模型** | "行为在外部 Service 而非实体上，这是有意的架构选择还是历史遗留？" |
| 混合：部分行为在实体，部分在 Service | **混合模型** | "哪些行为应该在实体上，哪些在 Service 上？划分理由是什么？" |

#### 贫血模型的探索策略

贫血模型下，探索业务行为**必须追踪 Domain Service**，不能只读 model：

1. **扫描 Service 的方法**：`*Service`/`*Manager`/`*Handler` 中操作实体的方法就是候选业务行为
2. **区分应用服务 vs 领域服务**：
   - 应用服务（编排）：`OrderAppService.placeOrder()` → 编排流程，不含业务规则
   - 领域服务（业务逻辑）：`PricingService.calculate(order)` → 含业务规则，真正的领域行为
   - 问用户区分："这个 Service 是编排流程，还是承载业务规则？"
3. **将领域服务的行为归入 domain-model.md 的"领域服务"节**，标注其操作哪个聚合、含什么业务规则

### Step 6 实现指导：共建聚合协作视图

通过一次一问澄清**业务级聚合协作**：

1. 哪些是核心聚合根（业务入口概念）？
2. 聚合间如何**协作完成业务用例**？（业务依赖性质，如"Worker 分配 依赖 Task 处于 Schedulable 状态"）
3. 有状态实体的状态机（业务状态与转换）？
4. **行为归属识别**：聚合的业务行为在实体本身（充血）还是外部 Service（贫血）？贫血模型下，必须追踪 Service 的业务行为并归入领域模型——只读实体方法会漏掉真实业务行为。

   > **何时跳过行为归属章节**：当 BC 无领域行为（纯数据/纯配置/纯路由，实体无业务方法且无 Domain Service）时，不生成 domain-model.md 的"行为归属与领域服务"章节，不强行识别贫血/充血——此时该判断无业务意义。

**`<anchor:ddd>` 列用业务术语**：聚合根/领域实体/值对象/领域服务列填**业务术语**（如"连接器工作器"），不是代码类名（如"WorkerConnector"）。代码类名归 `<anchor:code>` 列。**特例**：当代码类名本身就是业务术语时（如领域事件名 `ConnectorStarted`，或 Kafka 生态中 `Worker`/`Connector`/`Task` 等类名即通用术语），可使用类名。判断标准：该名称在项目领域中有明确的业务含义，而非纯实现描述（如 `InternalSinkRecord` 是实现描述，非术语）。

**代码锚点格式**：聚合根/实体/值对象/领域服务填 `类名`；协作视图填发起协作的方法 `类名.函数名`；状态机填执行转换的方法 `类名.函数名`；行为归属填行为所在类名。代码锚点**仅支持三类格式**：`类名` / `类名.函数名` / `HTTP方法:/路径`。禁止 `文件#类名`、文件路径等其他格式。

**重要：不产出字段级 ER 图。** 字段关系、外键、表结构由 graphify 提供。本 skill 只产出**聚合协作视图**——展示聚合如何协作完成业务，以及依赖的**业务性质**。这是代码里分散、graphify 查不出"为什么"的部分。

> 行为归属的理由（有意设计 / 历史遗留）融入技术约束的"模型风格"章节，不单独产出 decisions.md。

**产出**：各 BC 的 `docs/features/<bc-name>/domain-model.md` — 模板 [templates/business/domain-model.md](../../templates/business/domain-model.md)

## §8 模式识别：业务不变式（Step 7）

### 不变式的定位：聚合根对调用者的状态承诺

不变式是**聚合根对所有调用者的状态承诺**——无论被怎么操作，状态永远满足这些规则。违反即业务状态非法（不是错误，是状态破坏）。不变式定义了聚合操作完成后什么算合法状态，是事务边界的判定依据。聚合之所以是一个聚合，正是因为内部有这些"必须永远为真"的规则需要一起维护。

#### 三类规则的区分

提取时最常见的错误是把"接口契约"或"防御性编程"当成不变式。三者性质不同：

| 类型 | 时间维度 | 主体 | 违反意味着 | 例子 | 归属 |
|------|---------|------|-----------|------|------|
| **业务不变式** | 恒久为真（任何时刻） | 聚合根 | 业务状态非法（状态破坏） | 订单总金额 = 各订单项金额之和 | `invariants.md` |
| **接口契约** | 单次调用（前置/后置） | 接口/方法 | 本次调用失败（可重试/可补偿） | 调用 placeOrder 后状态变为 PLACED | `contracts.md` |
| **防御性编程** | 调用瞬间 | 参数/输入 | 调用方 bug | name 非空、count > 0 | 不记录 |

**判定问句**（共建时引导用户使用）：
- "这个规则违反后，业务对象即使重试或补偿也无法回到合法状态吗？" → 是 → 不变式
- "这条规则是单次调用前后的承诺吗？" → 是 → 接口契约（后置条件，归 contracts.md）
- "违反这条，是业务上不可恢复的，还是只是需要重试/补偿？" → 不可恢复 → 不变式

**少而精原则**：不变式应只保留"违反即业务状态非法"的核心规则。不设硬性下限——如果 BC 只有不显而易见的核心不变式 1 条，就记 1 条；如果没有，不生成本文件。如果提取出很多条（超过 10 条），大概率混入了防御性编程或接口契约，按上表重新筛选——只保留"违反即状态破坏"的规则。

**无状态业务无不变式**：不变式是聚合根概念。如果一个 BC 没有聚合根/有状态实体（纯计算、ETL、无状态转换 API、纯路由），不生成 invariants.md，在 BC index.md 标注 N/A。

**显而易见的不变式不记录**：任何合格开发者能从命名/结构直接推断的规则不记录。

### 不变式信号

不变式散落在校验、守卫、测试、注释里。代码能找到**实现**，但"这是业务规则还是防御性编程"需人确认——这是本 Step 的核心区分点。

| 代码信号 | 提问方向 |
|:---------|:------|
| 构造函数/setter 中的校验 | "这个校验是业务规则（违反即非法状态），还是防御性编程（参数合法性）？" |
| 跨字段校验（如 `if a then b required`） | "这个跨字段约束代表什么业务规则？还是只是输入验证？" |
| 状态机守卫（`if status != X then error`） | "为什么状态 X 不能转换到 Y？业务上发生了什么？" |
| 测试中的断言 | "这个测试断言验证的是业务不变式吗？" |
| 事务边界内的多个写操作 | "这些写操作在同一事务，是因为它们必须同时成功/失败吗？为什么？" |

### 不变式分类

> 不变式主要描述不变的业务关键约束，不应该关注防御性维度的内容。三类规则的区分见上文"三类规则的区分"表。

**每条不变式内容必须与用户澄清**

**不变式分类：**

| 类型 | 思考方向\提问方向 |
|:-------|:------|
| 跨字段不变式（单实体内） | "这个实体的字段间约束，业务上意味着什么？" |
| 跨聚合不变式 | "这两个聚合间的约束是如何维持的？最终一致还是强一致？" |
| 跨 BC 不变式 | "跨上下文的这个约束由谁保证？业务后果是什么？" |
| 生命周期不变式 | "这个状态序列是业务规定的吗？能否跳过某状态？" |


> 不变式散落在校验、守卫、测试、注释里。代码能找到**实现**，但"这是业务规则还是防御性编程"需人确认。

**产出**：各 BC 的 `docs/features/<bc-name>/invariants.md` — 模板 [templates/business/invariants.md](../../templates/business/invariants.md)

> 如果一个 BC 没有真正的业务不变式（只有防御性编程），不生成此文件，在 BC `index.md` 标注 N/A。

## §9 隐形架构决策提取

> graphify 能给出调用图、依赖图、类型关系——这些是**可见的架构**。但有一类架构知识 graphify 查不到：**为什么这么架构**。这些隐形架构决策散布在代码结构里，但理由只在人脑中。必须主动挖掘并问用户。

### 设计决策不再单独产出

本 skill **不产出**独立的 decisions.md。设计决策（为什么是现在的样子）按性质融入各约束的"理由/由来"字段中：

| 隐形架构决策的性质 | 归入的约束 | 写法 |
|:-------|:------|:------|
| 架构选型理由（为什么选某个架构风格） | 技术约束 | 写成规则："架构必须/应该……"，理由记入"选型理由"字段 |
| 一致性策略理由（为什么最终一致/强一致） | 业务不变式 + 技术约束 | 跨 BC 不变式在"业务理由"中注明保证方；事务实现选型理由归技术约束 |
| 模型风格理由（为什么贫血/充血） | 技术约束 | 写成规则："模型风格应该……"，理由记入"由来"字段 |
| 事务边界理由（为什么边界划在这里） | 业务不变式（一致性需求）+ 技术约束（事务模式选型） | 一致性需求写入不变式业务理由，事务实现选型写入技术约束 |
| BC 划分理由（为什么这么分） | 业务约束（context-map.md） | 记入 context-map 的关系说明 |

### 隐形架构的维度

| 维度 | graphify 能查到 | graphify 查不到（必须问用户） |
|:-------|:------|:------|
| 架构风格 | 目录结构 | 为什么选这个风格？考虑过替代方案吗？ |
| 事务边界 | 事务代码位置 | 为什么边界划在这里？业务上哪些操作必须原子？ |
| 一致性策略 | 同步/异步调用模式 | 为什么这里最终一致而非强一致？业务能接受什么程度延迟？ |
| 模型风格 | 实体方法数（贫血/充血信号） | 为什么这个 BC 贫血而那个充血？有意还是遗留？ |
| BC 划分 | 目录聚类 | 为什么这么分？有没有该独立却没独立的？ |
| 演进历史 | 当前状态 | 架构怎么演变成现在的样子？重构过吗？ |

### 提问策略

隐形架构决策往往用户自己也未必明确意识到。提问时要**带着代码信号帮用户回忆**：

> 我想理解架构选择。
>
> 代码里我看到：`runtime` 和 `storage` 之间所有调用都通过 trait 接口，但 `runtime` 和 `connect` 之间是直接调用具体类型。
> 这个差异说明前两者有明确边界，后两者关系更紧。
>
> 问题：`runtime` 和 `connect` 是有意设计成紧耦合的，还是还没来得及解耦？（A: 有意 / B: 待解耦 / C: 其他）

### 决策信号的代码定位点

代码显示当前实现，**完全不显示**：
- 为什么选这个方案
- 考虑过哪些替代方案
- 历史演变（为什么变成现在这样）
- 技术约束的由来

这些必须问用户。代码信号只能帮你**定位提问点**：

| 代码信号 | 提问方向 | 归入约束 |
|:---------|:------|:------|
| 特定的架构模式 | "为什么选这个架构？有历史原因吗？" | 技术约束 |
| 特定的一致性策略 | "为什么这里用最终一致而非强一致？业务上能接受吗？" | 业务不变式 |
| 特定的事务边界 | "为什么事务边界划在这里？业务上哪些操作必须原子？" | 业务不变式 + 技术约束 |
| 模型风格（贫血/充血） | "为什么这个 BC 贫血而那个充血？有意还是遗留？" | 技术约束 |
| 编码规约/约束（如 lint 规则） | "这些编码约束的由来？有踩过坑吗？" | 技术约束 |
| 性能相关代码（缓存/批处理/异步） | "这个性能优化是为了解决什么问题？" | 技术约束 |
| 看似奇怪的实现 | "这个实现看起来不直观，是有意的权衡还是遗留？" | 按性质归入对应约束 |

### 产物写法：规则而非过程

隐形架构决策在产物中写成**规则**（"必须/禁止/应该"），而非过程性描述。例：

✅ **规则写法**（正确）：
> 架构必须通过 trait 接口隔离 runtime 与 storage，禁止直接依赖具体类型。
> **由来**：storage 实现可能替换（如换存储引擎），接口隔离保证 runtime 不受影响。

❌ **过程写法**（错误）：
> 我们先建了 runtime，后来加了 storage，为了解耦用了 trait……

> 决策理由和替代方案**只能来自用户**。用户不知道的，标 UNKNOWN，不臆造。

## §10 非 DDD 代码库策略

当代码库没有 DDD 结构时，**业务边界仍需问用户**，代码信号用于生成提问方向：

### 过程式 / 事务脚本

| 代码信号 | 提问方向 |
|:---------|:------|
| 方法众多的大型 Service 类 | "这个大类里的方法，业务上是否属于不同的能力域？" |
| 跨 Service 共享的数据模型 | "这个共享模型是否应该按业务上下文拆分？" |
| 业务逻辑中直接写 SQL | "业务逻辑和数据访问混在一起，是历史原因吗？" |
| 对 status/type 字段的 `if/switch` | "这个状态分支逻辑，业务上代表什么状态机？" |

### 分层架构（Controller-Service-Repository）

| 层 | 提问方向 |
|:------|:------|
| Controller / Handler | "这些入口点对应哪些业务用例？" |
| Service 层 | "Service 里混了应用逻辑和领域逻辑吗？哪些是真正的业务规则？" |
| Repository 层 | "持久化是上下文内还是跨上下文？" |
| 共享 Model | "这个共享模型在不同业务场景下含义一致吗？" |

### 无清晰边界的单体

当目录不暗示任何领域分组时，**不要猜测**。按顺序尝试生成提问方向：

1. **数据库表分组** — "`orders_*` 表和 `inventory_*` 表是否对应不同业务域？"
2. **路由/端点分组** — "`/api/orders/*` 和 `/api/inventory/*` 是否对应不同业务能力？"
3. **大文件拆分** — "这个 500 行的 Service，里面的方法是否跨了多个业务上下文？"

如果以上都不产生结构 → **STOP**，请用户解释预期的业务边界。不要猜测。

### 降级策略：按代码 DDD 程度选择产物子集

并非所有代码库都有完整的 DDD 结构。根据代码库的实际形态，选择可产出的产物子集——**不强行套用 DDD 概念到不匹配的代码**。

| 代码库形态 | DDD 程度 | 可产出产物 | 不可产出（标记 N/A） |
|:---------|:--------:|:---------|:-----------------|
| 完整 DDD（清晰的领域模型+聚合根+持久化抽象） | 完整 | 全部 7 个产物 | — |
| 分层架构（有分层但无聚合根概念） | 部分 | context-map + business-flow + invariants + contracts | domain-model（无聚合）、domain-events（如无事件） |
| 过程式/事务脚本（大 Service 类，无领域模型） | 低 | context-map + business-flow + invariants | domain-model、domain-events、contracts（如无跨上下文调用） |
| 纯脚本（单一入口，无业务边界） | 极低 | context-map（单 BC）+ invariants（如有） | 其余全部 N/A |

**原则**：
- 领域模型（聚合/实体/值对象）的提取**适配代码形态**——过程式代码没有聚合，但可能仍有业务不变式（散落在 if 检查里）
- 不可产出的产物在 BC 的 `index.md` 中标记 N/A 并说明原因，不强行编造
- 即使 DDD 程度低，**业务边界（context-map）始终可产出**；业务不变式（invariants）按需生成，不要生成无业务意义的内容。
