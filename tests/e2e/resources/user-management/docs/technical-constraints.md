# 技术约束 — User Management System

---

## 1. 业务实现技术

### 1.1 设计模式

### TC-001: 聚合根 + 值对象模式
- **选型理由（Why）**: 用户身份需要强一致性边界，Profile 作为值对象保证不可变性
- **实现规则**: User 作为聚合根封装所有状态变更；Profile 为不可变值对象，变更时创建新实例
- **代码锚点**: `User`
- **适用范围**: BC-01

### TC-002: 仓储模式
- **选型理由（Why）**: 隔离领域逻辑与数据访问细节，便于测试时替换为内存实现
- **实现规则**: 所有持久化操作通过 UserRepository 接口，领域层不直接操作存储
- **代码锚点**: `UserRepository`
- **适用范围**: BC-01

### 1.2 算法选择

### TC-003: 密码哈希算法
- **选型理由（Why）**: 密码不可明文存储，使用加盐哈希防止彩虹表攻击
- **实现规则**: 密码长度 >= 8 字符；使用 bcrypt 风格的加盐哈希（测试用简化实现）
- **代码锚点**: `PasswordHasher.hash`
- **适用范围**: BC-02

### 1.3 架构模式

### TC-004: 分层架构
- **选型理由（Why）**: 控制器-服务-仓储分离关注点，每层有独占职责
- **实现规则**: 控制器只做 HTTP 解析和响应；服务编排业务逻辑；仓储处理持久化
- **代码锚点**: `AuthController`
- **适用范围**: 全局

### 1.4 安全模型

### TC-005: JWT 令牌认证
- **选型理由（Why）**: 无状态认证适合水平扩展，无需服务端会话存储
- **实现规则**: 令牌携带 userId 和 email，有过期时间；中间件验证 Bearer token
- **代码锚点**: `JwtManager.generateToken`
- **适用范围**: BC-02

## 2. 编码规范

### 2.1 错误处理

### TC-006: 业务异常用 Error 抛出
- **选型理由（Why）**: 测试项目保持简单，生产环境应使用自定义错误类
- **实现规则**: 业务规则违反时 throw new Error(message)；控制器层 try-catch 转为 HTTP 响应
- **代码锚点**: `AuthController.handleRegister`
- **适用范围**: 全局
